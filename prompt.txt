
### Endpoints

POST /api/upload
  - Accepts multipart file (CSV or parquet)
  - Parses to DataFrame, stores in memory with a UUID dataset_id
  - Returns: { dataset_id, name, rows, columns, preview: first 5 rows as JSON }

POST /api/analyse
  Body: { dataset_id: str, intent: str, depth: "quick" | "deep" | "stress" }
  - Runs full pipeline (see Pipeline section below)
  - Streams progress events as newline-delimited JSON so frontend can show live progress
  - Each event: { stage: str, message: str, progress: 0-100 }
  - Final event: { stage: "complete", findings: [...], model: {...}, stress_test: {...} }

GET /api/dataset/{dataset_id}
  - Returns dataset metadata + preview

GET /api/findings/{dataset_id}
  - Returns ranked findings array

GET /api/model/{dataset_id}
  - Returns model metrics, feature importance, training provenance

GET /api/stress/{dataset_id}
  - Returns stress test results

POST /api/consultant
  Body: { dataset_id: str, message: str, history: [{role, content}] }
  - Streams response from Ollama with full context injected
  - Returns Server-Sent Events stream

GET /api/report/{dataset_id}
  - Returns structured report JSON (used by frontend to render PDF)

GET /api/hardware/status
  - Returns { nrf_connected: bool, nrf_data: {...} | null }
  - Never fails — if hardware not present, returns nrf_connected: false

GET /api/ws/live
  - WebSocket endpoint
  - Streams live sensor data if nRF54LM20 connected
  - Streams { source: "nrf", timestamp, values: {...}, anomaly: bool | null }
  - If no hardware, sends keepalive ping every 5s so frontend connection stays open

## ANALYSIS PIPELINE

Run these stages in order. Emit a progress SSE event after each stage completes.

### Stage 1: Schema Inference (schema_inference.py)
For each column detect:
  - dtype: numeric / categorical / datetime / boolean / text
  - For numeric: min, max, mean, std, null_pct, is_time_series (True if monotonically increasing or named with time keywords)
  - For categorical: cardinality, top values
  - For datetime: range, inferred frequency
Return a schema dict. Emit { stage: "schema", message: "Schema inferred — {n} columns, {k} time-series detected", progress: 10 }

### Stage 2: Data Quality Score (data_quality.py)
Compute:
  - completeness: 1 - mean(null_pct across columns)
  - outlier_rate: fraction of rows with any column > 3 std from mean
  - drift_score: for time-series columns, compute coefficient of variation across rolling windows. High drift = low score.
  - overall_quality: weighted mean of above, 0-1
Emit { stage: "quality", message: "Data quality scored — {score:.0%} overall", progress: 20 }

### Stage 3: Hypothesis Generation (llm_client.py -> Ollama)
Build a prompt:
  System: "You are a senior quantitative analyst. Given a dataset schema and a user's analytical intent, return a JSON analysis plan. Return ONLY valid JSON, no preamble, no markdown."
  User: "Schema: {schema_json}\n\nIntent: {intent}\n\nReturn a JSON object with key 'hypotheses': an array of up to 6 objects, each with keys: 'name' (short title), 'type' ('correlation'|'anomaly'|'trend'|'leading_indicator'|'regime_change'), 'target_column' (column to analyse), 'feature_columns' (array of columns to use), 'description' (one sentence)."
Call Ollama at http://localhost:11434/api/generate, model llama3.1:8b, stream: false
Parse response JSON. If malformed, fall back to generating 3 default hypotheses from the schema (top numeric columns).
Emit { stage: "hypotheses", message: "Analysis plan generated — {n} hypotheses", progress: 30 }

### Stage 4: Stats Pipeline (stats_pipeline.py)
For each hypothesis, run the appropriate analysis:

CORRELATION:
  - Pearson and Spearman r between target and each feature
  - p-value for each
  - Return top 5 correlations with r, p, direction

ANOMALY:
  - Fit IsolationForest on the relevant columns
  - Return anomaly rate, top anomalous rows (as row indices + anomaly score)
  - Also run CUSUM on time-series columns if present

TREND:
  - STL decomposition (statsmodels) on the target column
  - Return trend direction, seasonality strength, residual variance

LEADING_INDICATOR:
  - Granger causality test between feature columns and target column at lags 1-5
  - Return lag with lowest p-value per feature pair

REGIME_CHANGE:
  - CUSUM or PELT changepoint detection on target column
  - Return changepoint locations + magnitude

Emit { stage: "stats", message: "Statistical analysis complete — {n} tests run", progress: 55 }

### Stage 5: Model Builder (model_builder.py)
  - Select target column: highest-variance numeric column not used as a feature, or the column most referenced in the intent (ask Ollama to pick if ambiguous, one-word response)
  - Feature columns: all numeric columns except target
  - Drop rows with null in target
  - Train/test split: 80/20, shuffle=False if time-series detected
  - Train LightGBM regressor (or classifier if target is binary/categorical)
  - Compute SHAP values for feature importance
  - Record: model_type, accuracy (R2 or F1), feature_importance (column -> shap_value), training_rows, training_time_ms, trained_on: "ASUS GX10 (remote)" if SSH available else "local"
  - If depth == "quick": use 100 estimators. If "deep" or "stress": 500 estimators.
Emit { stage: "model", message: "Model trained — {metric_name}: {metric_value:.3f}", progress: 70 }

### Stage 6: Stress Tester (stress_tester.py) — only if depth != "quick"
  - Take the top 5 features by SHAP importance
  - For each feature, perturb by: -50%, -25%, +25%, +50%, +100%, set to min, set to max, set to 0
  - Record model output change and confidence change for each perturbation
  - Flag as STABLE (green) if output changes < 10%, DEGRADED (amber) if 10-30%, BROKEN (red) if > 30%
  - Find the 3 worst edge cases: specific combination of feature values where model confidence drops most
  - Format edge cases as plain-English descriptions
Emit { stage: "stress", message: "Stress test complete — {n_broken} critical edge cases found", progress: 85 }

### Stage 7: Finding Ranker + LLM Explanations (finding_ranker.py + llm_client.py)
  - Rank all findings by: primary sort = statistical significance (p-value ascending, anomaly score descending), secondary sort = effect size
  - For each top 5 finding, call Ollama:
    Prompt: "You are a senior data analyst. Explain this finding in 2 sentences for a non-technical executive. Finding: {finding_json}. Dataset intent: {intent}. Return only the explanation, no preamble."
  - Attach explanation to each finding
Emit { stage: "findings", message: "Findings ranked — {n} significant signals identified", progress: 95 }

### Stage 8: Report Generation
  - Compile all outputs into a structured report dict
  - Call Ollama once for executive summary (3-4 sentences)
  - Store report in dataset store
Emit { stage: "complete", message: "Analysis complete", progress: 100, report_ready: true }

## OPTIONAL HARDWARE (nRF54LM20 over BLE)

### ble_listener.py
  - Try to import bleak at module load time. If ImportError, set HW_AVAILABLE = False and all functions return None gracefully.
  - If bleak available, scan for BLE devices advertising service UUID "12345678-1234-1234-1234-123456789abc" (the Signal service UUID — hardcode this, tell user to use same UUID in firmware)
  - On connect, subscribe to characteristic for sensor data (notify)
  - Parse incoming bytes: struct format "fffB" = temperature (float), humidity (float), pressure (float), anomaly_flag (uint8)
  - Emit parsed readings to an asyncio queue consumed by the WebSocket endpoint
  - Reconnect automatically on disconnect with 2s backoff
  - Status endpoint returns connected device name + RSSI + last_reading + last_anomaly_timestamp

### Integration rules
  - Hardware is NEVER required for any analysis feature
  - If hardware not connected: Live Monitor screen shows a "No hardware connected" empty state with instructions for connecting the nRF54LM20 DK
  - If hardware connected: Live Monitor shows live waveforms and anomaly feed
  - Hardware data can be optionally included as a dataset: button in Live Monitor "Add to analysis" streams the last N readings into a new dataset_id and runs the full pipeline on it
  - The hardware section in the demo script is clearly optional — "if we had the nRF54LM20 connected, you'd see live edge inference here"

## ANALYSIS PROGRESS — REAL-TIME

Use EventSource (SSE) to consume the /api/analyse stream.
Each event updates the dataset status in global state.
The Overview tab subscribes to this and renders events as they arrive.
On stage "complete", fetch full results from the individual endpoints and populate the dataset in state.

---

## ERROR HANDLING

All errors must be graceful. Rules:
  - If Ollama offline: skip LLM stages, use auto-generated finding titles and no explanations. Show "LLM offline — connect GX10 for AI explanations" banner in amber at top of analysis view. All stats still run.
  - If hardware not present: all hardware features show empty state, nothing breaks.
  - If dataset has < 50 rows: show warning "Small dataset — results may not be statistically reliable" but run anyway.
  - If a stats test throws an exception: catch it, log it, skip that finding, continue.
  - Never show a Python traceback to the user. Always show a human-readable error message.
